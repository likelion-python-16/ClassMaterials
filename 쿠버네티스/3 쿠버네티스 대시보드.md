배포(Deployment)의 의미
일반 의미: 어떤 애플리케이션을 실행 환경에 올려놓는 것  
→ 로컬 테스트, 스테이징 서버, 운영 서버에 올려두는 행위 전부 배포라고함.

Docker Compose vs Kubernetes YAML
- Docker Compose (`docker-compose.yml`)
    - 로컬 개발/단일 서버에서 여러 컨테이너를 올리고 연결할 때 사용.
    - 예: `app`, `db`, `redis` 컨테이너 정의하고 `docker compose up`으로 실행.
    - 배포 환경을 단순화해줌.
        
- Kubernetes 매니페스트 (`deploy/k8s/*.yaml`)
    - 클러스터 환경에서 컨테이너를 실행·관리.
    - Compose가 하는 일을 더 세밀하고 강력하게 나눔:
        - `Deployment` → Pod(컨테이너) 관리
        - `Service` → 네트워크 연결
        - `Ingress` → 외부 접근
        - `ConfigMap/Secret` → 환경 변수, 비밀 관리
    - 실행은 `kubectl apply -f …`
        
즉, 쿠버네티스에서는 Compose 파일을 쓰지 않고, 각 역할별 yaml 파일을 작성합니다.

관계를 정리하면 다음과 같습니다.
- `Dockerfile ` 
    → 이미지 빌드 (공통, 반드시 필요)
- `docker-compose.yml ` 
    → 단일 서버 환경에서 컨테이너 실행/연결 (쿠버네티스 안 쓰는 경우)
- `deploy/k8s/*.yaml ` 
    → 쿠버네티스 클러스터에서 컨테이너 실행/연결 (Compose 대체)

==`결론은 Dockerfile은 항상 필요 (이미지 빌드용).`==
==`쿠버네티스를 쓰면 docker-compose.yml은 필요 없음.`==
==`대신 deploy/k8s/*.yaml이 Compose의 역할을 나눠서 담당.`==

**상태 확인 및 해설**

✅ 1. 메타데이터
- 이름: `ai` → Deployment 리소스 이름
- 네임스페이스: `app-dev` → 해당 리소스가 속한 논리적 구역
- 생성 시간: 2 days ago → 언제 배포했는지
- UID: 내부적으로 리소스를 구분하기 위한 고유 ID
    
👉 CLI에서 `kubectl describe deployment ai -n app-dev` 하면 같은 정보가 나옵니다.

---
✅ 2. 리소스 정보
- 전략(Strategy): `RollingUpdate`  
    → 새 버전 배포 시 한꺼번에 갈아치우는 게 아니라, 조금씩 교체하면서 무중단 배포
- 최소 준비 시간: 0초
- 리비전 내역 보존: 10 → 이전 버전의 ReplicaSet을 10개까지 기록 유지
    
---
✅ 3. 롤링 업데이트 정책
- 최대 증가 수(surge): 25%
- 최대 불용 수(unavailable): 25%
    
👉 예: replicas=4일 때 새 버전을 올리면, 최대 5개까지 늘릴 수 있고(25% 증가), 최소 3개 이상은 항상 살아있어야 함(25% 불용).  
즉, 무중단 배포를 위한 안전장치.

---
✅ 4. 파드 상태
- 업데이트된(Updated): 1
- Total(전체): 1
- 가용(Available): 1
    
👉 지금은 1개의 Pod만 운영되고 있으며 정상적으로 가용 상태임.

---
✅ 5. 조건(Conditions)
두 가지 상태가 기록되어 있음:
1. Available = True
    - 최소 가용 Pod 개수 충족
    - 메시지: `Deployment has minimum availability`
        
2. Progressing = True
    - 새 ReplicaSet이 정상적으로 진행 중
    - 메시지: `ReplicaSet "ai-64964f45d9" has successfully progressed.`
        
👉 두 조건이 모두 `True`이므로, Deployment가 정상적으로 동작 중이라는 뜻입니다.

요약하여 정리하면 
- 롤링 업데이트(RollingUpdate): 앱을 중단하지 않고, Pod를 하나씩 새 버전으로 교체하는 방식.
- 불용수(maxUnavailable): 교체 중에 잠깐 빠져도 괜찮은 Pod 수(비율).
- 25% 의미: 전체 Pod 개수의 25%까지는 동시에 비워져도 허용한다는 뜻.

앱이 클러스터에 잘 배포되었고, Pod가 정상 상태(Ready)이며, 리소스 사용량도 문제가 없는지 검증한 거예요

2단계 — 환경 변수 & 내부 통신 (ConfigMap/Secret/Service)

`1)` ConfigMap 적용
```bash
kubectl -n app-dev apply -f deploy/k8s/config.yaml
```
- ConfigMap: 환경 변수나 설정값을 Pod 안에서 쓰도록 전달하는 리소스
- 예: DB 주소, API URL, DEBUG 모드 값 등
- 소스코드에 하드코딩하지 않고 외부에서 관리하기 위함

`2)` Secret 적용
```bash
kubectl -n app-dev apply -f deploy/k8s/secret.yaml
```
- Secret: 비밀번호, API 키, 인증 토큰 같은 **민감한 값**을 저장하는 리소스
- ConfigMap과 비슷하지만 base64로 인코딩해서 보관
- Pod 안에서는 환경 변수로 주입하거나 파일로 마운트해서 사용

`3)` Service 적용
```bash
kubectl -n app-dev apply -f deploy/k8s/svc-api.yaml
```
- Service: Pod의 고정된 접근 주소를 만들어 줌
- Pod는 죽고 다시 생성되면 IP가 바뀌는데, Service가 DNS 이름(api.app-dev.svc.cluster.local)으로 안정적인 통신 제공
- 내부 통신(예: `api` ↔ `db`)을 가능하게 해줌

`4)` 상태 확인
```bash
kubectl -n app-dev get cm,secret,svc
```
ConfigMap, Secret, Service가 정상 생성되었는지 확인하는 명령어

3단계 — 외부 접근 (Ingress)

`0)` 준비확인
```bash
minikube start --driver=docker
kubectl config use-context minikube
minikube addons enable ingress
kubectl -n ingress-nginx get pods 
# controller가 Running 될 때까지 대기

kubectl -n app-dev get deploy,po,svc         
# api/ai 서비스가 떠있는지 확인

kubectl -n app-dev get endpoints api ai      
# Pod IP:Port가 붙는지 확인
```

`1)` Ingress 매니페스트 작성 (nip.io + 포트포워드 겸용)
- hosts를 2개 넣어 두면 어디서든 접근이 편해요.
    - `demo.<minikube-ip>.nip.io` : (직접/터널 접근용)
    - `demo.127.0.0.1.nip.io` : (포트포워드 접근용)
`deploy/k8s/ingress.yaml` (핵심만)
```python
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-root
  namespace: app-dev
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
    # 루트("/")로 들어오면 /docs로 랜딩 (선택)
    nginx.ingress.kubernetes.io/app-root: "/docs"
spec:
  ingressClassName: nginx
  rules:
  - host: demo.<MINIKUBE_IP>.nip.io 
  # 예: demo.192.168.49.2.nip.io
    http:
      paths:
      - path: /
        pathType: Prefix
        backend: { service: { name: api, port: { number: 80 } } }
      - path: /ai
        pathType: Prefix
        backend: { service: { name: ai,  port: { number: 8001 } } }
  - host: demo.127.0.0.1.nip.io  # 포트포워드용
    http:
      paths:
      - path: /
        pathType: Prefix
        backend: { service: { name: api, port: { number: 80 } } }
      - path: /ai
        pathType: Prefix
        backend: { service: { name: ai,  port: { number: 8001 } } }
```

`2)` Ingress 적용 (IP 자동 치환)
```bash
MINI_IP=$(minikube ip)
sed "s/<MINIKUBE_IP>/$MINI_IP/g" deploy/k8s/ingress.yaml | kubectl -n app-dev apply -f -

# 충돌 방지: 불필요한 예전 Ingress가 있으면 삭제
kubectl -n app-dev get ingress
# 필요 시: kubectl -n app-dev delete ingress app app-local-ai app-local-root

# 적용 확인
kubectl -n app-dev get ingress -o wide
kubectl -n app-dev get ingress app-root -o jsonpath='{range .spec.rules[*]}{.host}{"\n"}{end}'
# -> demo.<MINI_IP>.nip.io / demo.127.0.0.1.nip.io 가 보여야 정상
```

인그레스 외부 접속 = 쿠버네티스 건물의 정문을 열고, 들어온 손님을 방(서비스)으로 안내하는 것. 
(minikube에선 ‘거리’가 인터넷이 아니라 내 PC(호스트 OS) 쪽이라고 생각하면 돼요.)


이 방식이 좋은 이유
- 하나의 도메인으로 여러 서비스 라우팅: `/`, `/ai`, `/api/v1` 등 경로별로 다른 백엔드 연결.
    
- 현실(운영)과 동일한 접근 형태: 도메인/HTTPS/리다이렉트/헤더 등 실서비스 패턴을 로컬에서 재현.
    
- TLS/인증/레이트리밋 등 공통 정책을 정문 한 곳에서 처리.
    
- NodePort 대잔치 방지: 서비스마다 포트 열어두는 번거로움·보안 리스크 감소.
    
- 롤링업데이트/스케일링과 자연스럽게 연동: 뒤에서 Pod가 바뀌어도 정문 URL은 그대로.
    

로컬(minikube)에서 특히 이렇게 한 이유
- 로컬은 퍼블릭 인터넷이 아니라 내 PC에서 내 로컬 클러스터로 들어오는 길만 열면 됨.
    
- 그래서 포트포워드**(또는 `minikube tunnel`) + nip.io 도메인으로 운영과 비슷한 URL 경험을 만들고, Swagger로 끝단(브라우저)까지 확인한 것.

4단계 — 오토스케일링(HPA) 데모

HPA 데모 시나리오 (Minikube + metrics-server)

목표
- 서비스가 갑자기 바빠지면 자동으로 파드 수가 늘고(scale-out),
- 트래픽이 줄면 자동으로 다시 줄어든다(scale-in)는 걸 눈으로 증명.
    
등장 리소스
- `Deployment/php-apache` : CPU 요청량 `200m`(0.2 vCPU)로 실행되는 웹 컨테이너
- `Service/php-apache` : 클러스터 내부 DNS `http://php-apache`
- `HPA/php-apache` : CPU 평균 사용률 50%가 목표 (즉, 파드 당 100m 이상 쓰면 확장)
- `Pod/load`(busybox) : 지속적으로 `wget`을 날려 부하를 만드는 역할


사전 확인 : 컨텍스트/네임스페이스/메트릭 확인
```bash
# 컨텍스트 / 네임스페이스
kubectl config use-context minikube
kubectl get ns app-dev || kubectl create ns app-dev

# metrics-server 동작 확인
kubectl top nodes           # 숫자 나오면 OK
```

앱 배포 + 서비스 생성
```bash
# (A) 배포 + 서비스
kubectl -n app-dev apply -f - <<'YAML'
apiVersion: apps/v1
kind: Deployment
metadata: { name: php-apache, namespace: app-dev }
spec:
  replicas: 1
  selector: { matchLabels: { app: php-apache } }
  template:
    metadata: { labels: { app: php-apache } }
    spec:
      containers:
      - name: php-apache
        image: registry.k8s.io/hpa-example
        ports: [{ containerPort: 80 }]
        resources:
          requests: { cpu: 200m }
          limits:   { cpu: 500m }
---
apiVersion: v1
kind: Service
metadata: { name: php-apache, namespace: app-dev }
spec:
  selector: { app: php-apache }
  ports: [{ port: 80, targetPort: 80 }]
YAML
```

HPA (CPU 50% 넘으면 1~5개로 자동 확대)
```bash
kubectl -n app-dev apply -f - <<'YAML'
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: php-apache, namespace: app-dev }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: php-apache }
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 50 }
YAML
```

기대 상태(평시)
- 파드 1개(`Ready 1/1`)
- `kubectl -n app-dev get hpa php-apache` 에서 `TARGETS` 가 `~0%/50%` 근처
- 대시보드(네임스페이스 `app-dev`) → 워크로드 → 디플로이먼트 → php-apache
    - 원하는 복제본/가용 복제본이 **1/1**

GUI 위치:  
상단 네임스페이스 `app-dev` → 워크로드 → 디플로이먼트 → php-apache  
→ Desired/Available 복제본 수가 1→2→3…로 증가하는지 확인  
(부하 중단하면 수 분 내 감소)

---
트래픽 급증!
부하 걸기(새 터미널에서)
```bash
# app-dev 네임스페이스에 로드 제너레이터 파드 실행
kubectl -n app-dev run -it --rm load --image=busybox -- /bin/sh
# busybox 셸 안에서 엔터:
while true; do wget -q -O- http://php-apache >/dev/null; done
```
- 각 파드 CPU 사용률이 요청량(200m)의 50% = 100m을 넘기 시작
- HPA가 “목표(50%)”보다 높다고 판단 → 복제본 수를 2, 3… 으로 점진적 증가

---
관찰포인트
스케일 변화 관찰 (둘 다 켜두면 좋아요)
```bash
# 터미널 A: HPA 상태 변화를 라이브로
kubectl -n app-dev get hpa php-apache -w

# 터미널 B: 디플로이먼트/파드 개수 변화
kubectl -n app-dev get deploy php-apache -w
kubectl -n app-dev get pods -l app=php-apache -w

# (옵션) 실사용량 보기
kubectl -n app-dev top pods -l app=php-apache
```
A: `TARGETS` 예: `180%/50%` 처럼 목표 초과가 보이며 `DESIRED`/`CURRENT`가 올라감

B: 드가 `2/3/…` 개로 늘어나는 모습
대시보드
- 디플로이먼트 상세에서 복제본 수 증가
- 이벤트 섹션에 `Scaled up` 메시지

---
안정 구간
- 파드가 여러 개로 늘면 각 파드에 들어오는 요청이 분산되어 평균 CPU가 목표(50%) 근처로 안정
- HPA `TARGETS`가 목표에 수렴하도록 복제본 수를 유지한다

---
트래픽 감소 → 자원 회수
정리(원복하고 싶을때)
```bash
kubectl -n app-dev delete hpa php-apache
kubectl -n app-dev delete deploy php-apache
kubectl -n app-dev delete svc php-apache
```
- 로드 제너레이터 터미널에서 `Ctrl+C`, 그 다음 `exit` 로 종료
- 잠시 후 평균 CPU가 떨어지면 HPA가 복제본 수를 1까지 서서히 감소
- 대시보드/CLI에서 `Scaled down` 이벤트와 복제본 감소를 확인
