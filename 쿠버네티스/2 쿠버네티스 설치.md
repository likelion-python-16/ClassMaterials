kubectl 설치 (CLI 도구)
```bash
# 1) 준비
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg

# 2) 키링 폴더 만들고 GPG 키 등록

curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.30/deb/Release.key \
  | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-archive-keyring.gpg

# 3) 쿠버네티스 APT 저장소 등록
echo "deb [signed-by=/etc/apt/keyrings/kubernetes-archive-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.30/deb/ /" | sudo tee /etc/apt/sources.list.d/kubernetes.list > /dev/null

# (권장) 키 파일 권한 정리
sudo chmod 644 /etc/apt/keyrings/kubernetes-archive-keyring.gpg

# 4) 설치
sudo apt-get update
sudo apt-get install -y kubectl

# 5) 확인
kubectl version --client
```

매니페스트(Manifest) = YAML 파일

쿠버네티스에서 `Deployment`, `Service`, `ConfigMap` 같은 리소스를 정의한 YAML 파일을 매니페스트(Manifest)라고 부릅니다.

**쿠버네티스에서 리소스(Resource)란?**
쿠버네티스가 관리하는 모든 “대상 객체”를 리소스라고 불러요.  
예를 들어:
- Namespace → 작업 공간
- Pod → 컨테이너 1개 이상 실행 단위
- Deployment → Pod를 관리하는 컨트롤러
- Service → 네트워크 접근 창구
- ConfigMap / Secret → 설정 값 저장소
- Ingress → 외부에서 들어오는 HTTP 진입점
- HPA → 자동 스케일링 규칙
    
이런 것들이 전부 쿠버네티스 “리소스”입니다.

정의한다의 의미란?
쿠버네티스는 “상태 기반” 시스템이에요.  
사용자가 “원하는 상태(desired state)”를 YAML로 정의하면,  
쿠버네티스가 그 상태를 맞춰주는 것이에요.

---
###### Docker의 관점

- Docker는 **명령 기반(imperative)** 도구에 가깝습니다.
	
- 사용자가 직접:
    `docker run -d -p 8000:8000 myapp:latest`
    → 이러면 컨테이너 1개 실행.

- 컨테이너가 죽으면? 👉 **자동 복구 없음.** (사용자가 다시 실행해야 함)
- 5개 띄우고 싶으면? 👉 직접 `docker run` 5번 or `docker-compose up --scale` 실행해야 함.
    
➡️ 즉, Docker는 “내가 시킨 대로 한 번 실행”이지, “원하는 상태를 유지하는 시스템”은 아님.

---
###### Kubernetes의 관점

- 쿠버네티스는 **선언적(Declarative)** 상태 기반 시스템.
    
- 사용자가 “원하는 상태(desired state)”를 정의하면:
    `kind: Deployment spec:   replicas: 3`
    → “Pod가 항상 3개 있어야 해” 라고 선언.
    
- 실제 상태가 Pod 2개뿐이면? 👉 쿠버네티스가 1개 더 띄워서 3개를 맞춤.
- Pod 하나 죽으면? 👉 자동으로 새로 생성해서 3개 유지.
    
➡️ 즉, 쿠버네티스는 **원하는 상태와 실제 상태를 항상 동기화**합니다.

---
디렉토리 구조로 이해하기
```
my-project/
├─ docker-compose.yml   # 로컬 개발용
├─ Dockerfile           # 이미지 빌드용
└─ k8s/                 # 쿠버네티스 운영용
   ├─ namespace.yaml
   ├─ config.yaml
   ├─ secret.yaml
   ├─ deploy-api.yaml # 실제 컨테이너 실행과 유지 관리를 알아서 해줌
   ├─ svc-api.yaml
   ├─ svc-ai.yaml
   ├─ ingress.yaml
   └─ hpa-api.yaml  # 스케일링 자동화 담당
```
나머지 파일들의 역할 (보조/환경/네트워킹)
- **namespace.yaml** → 리소스들을 모아 관리할 “작업 공간”
- **config.yaml** → 환경변수(ConfigMap) (앱 설정값 전달)
- **secret.yaml** → 민감정보(비번, 토큰) 관리
- **svc-api.yaml / svc-ai.yaml** → Pod 묶음을 고정 주소로 연결 (서비스 발견/내부통신)
- **ingress.yaml** → 클러스터 외부 → 내부 서비스 라우팅 (외부 접근창구)

따라서 쿠버네티스에서는 사용자가 직접 내가 원하는 상태(desired state)를 매니페스트(YAML 파일)에 적습니다. 
그리고 `kubectl apply -f <파일명>` 을 실행하면 쿠버네티스가 클러스터 안의 실제 상태(actual state)를 내가 선언한 상태와 맞추려고 자동으로 조정합니다.

우리는 처음 쿠버네티스를 사용해보는 것이므로 가장 기초적이지만 경험을 해볼수 있는 8개의 매니페스트를 사용하여 쿠버네티스 사용의 감을 잡으며 
앱 하나 배포 → 내부통신 → 외부접속 → 자동 확장 순의 흐름으로 경험을 해보는 것이 중요합니다.

---
아래 8개 매니페스트 파일의 역할 요약
- **namespace.yaml**  
    → “내 작업 공간(폴더)” 만들기
    
- **config.yaml**  
    → 공개 환경변수(예: APP_ENV=dev)
    
- **secret.yaml**  
    → 비밀값(예: SECRET_KEY, DB_PASSWORD)
    
- **deploy-api.yaml**  
    → API 서버 Pod를 항상 2개 이상 유지 (=컨테이너 자동 관리)
    
- **svc-api.yaml**  
    → API Pod 묶음을 하나의 고정 주소(`api`)로 접근 가능
    
- **svc-ai.yaml**  
    → AI Pod 묶음을 하나의 고정 주소(`ai`)로 접근 가능
    
- **ingress.yaml**  
    → 외부에서 `demo.local/` → API, `/ai` → AI 라우팅
    
- **hpa-api.yaml**  
    → CPU 부하 따라 자동 스케일링 (2~5개)

Kubernetes 매니페스트 작성

`deploy/k8s/namespace.yaml`
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: app-dev
```
`namespace.yaml` — 네임스페이스
- 무엇: `app-dev`라는 이름의 “작업 공간”을 만들며 클러스터 안의 “폴더/공간” (이 안에 모든 리소스를 깔아놓고 정리)
- 왜: 리소스를 한 데 묶어 깔끔하게 관리(삭제/조회/권한)하려고.
- 지금 필요? ✔️ 거의 항상 추천. (없어도 되지만, 쓰는 습관이 좋아요)
---
`deploy/k8s/config.yaml`
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: app-dev
data:
  APP_ENV: "dev"
  AI_URL: "http://ai:8001"
```
`config.yaml` — ConfigMap
- 무엇: `APP_ENV=dev`, `AI_URL=http://ai:8001` 같은 공개해도 되는 환경설정(.env) (예: APP_ENV, API URL)
- **왜**: 이미지를 바꾸지 않고도 환경값만 교체하려고.
- 지금 필요? 환경변수 쓰면 편함.(없어도 앱 코드에서 기본값으로 가능)

---
`deploy/k8s/secret.yaml` (민감값 있으면 여기에. 지금은 예시용.)
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
  namespace: app-dev
type: Opaque
stringData:
  SECRET_KEY: "change-me"
```
`secret.yaml` — Secret
- 무엇: 민감한 비밀번호 .env (예: SECRET_KEY, DB 비번)같은 민감값을 안전하게 저장.
- 왜: 깃에 비번 박제하지 않으려고.
- 지금 필요? 민감값이 있다면 필수.(처음 실습 땐 없어도 됨)

---
`deploy/k8s/deploy-api.yaml`
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: app-dev
spec:
  replicas: 2
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
        - name: api
          image: api:dev    # minikube 내부에 빌드할 예정
          imagePullPolicy: IfNotPresent
          ports: [{ containerPort: 8000 }]
          envFrom:
            - configMapRef: { name: app-config }
            - secretRef:    { name: app-secret }
          readinessProbe:
            httpGet: { path: /healthz, port: 8000 }
            initialDelaySeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: 8000 }
            initialDelaySeconds: 15
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }
```
`deploy-api.yaml` — Deployment(웹 API)
- 무엇: `api:dev` 이미지로 레플리카 2개를 항상 유지. 헬스 체크(프로브) 포함.
- 왜: Pod가 죽으면 자동 복구, 롤링 업데이트, 스케일 조정 등 “운영 기본기”로, Pod(컨테이너) 관리 로봇. 죽으면 다시 띄우고, 개수를 늘리고/줄임
- 지금 필요? 사실상 필수.(단순 Pod보다 Deployment가 표준)

---
`deploy/k8s/svc-api.yaml`
```yaml
apiVersion: v1
kind: Service
metadata:
  name: api
  namespace: app-dev
spec:
  type: ClusterIP
  selector: { app: api }
  ports:
    - port: 80
      targetPort: 8000
```
`svc-api.yaml` — Service(API용)
- 무엇: 라벨( `app: api` )을 가진 Pod들에 안정적인 내부 IP를 부여.
- 왜: Pod가 바뀌어도 접속 주소(api 서비스 이름)가 고정.
- 지금 필요? 일반적으로 필수.(Port-forward만 쓸 거면 잠깐 생략 가능)

전제: 경로 구조가 `app: api`로 일치해야 합니다.

---
`deploy/k8s/svc-ai.yaml`
```yaml
apiVersion: v1
kind: Service
metadata:
  name: ai
  namespace: app-dev
spec:
  type: ClusterIP
  selector: { app: ai }
  ports:
    - port: 8001
      targetPort: 8001
```
`svc-ai.yaml` — Service(AI용)
- 무엇: AI Pod에 고정 주소를 부여(예: `http://ai:8001`).
- 왜: API가 AI를 서비스 이름(ai) 으로 찾게 하려고.
- 지금 필요? API→AI 내부통신이 있으면 필수.
---
`deploy/k8s/ingress.yaml`
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app
  namespace: app-dev
  annotations:
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
spec:
  rules:
    - host: demo.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: api, port: { number: 80 } }
          - path: /ai
            pathType: Prefix
            backend:
              service: { name: ai, port: { number: 8001 } }
```
`ingress.yaml` — Ingress(정문)
- 무엇: `demo.local` 도메인의 `/ → api`, `/ai → ai` 라우팅 규칙.
- 왜: 브라우저에서 “도메인/경로”로 접근하려고(리버스 프록시).
- 전제: NGINX Ingress Controller 설치되어 있어야 동작  
    `minikube addons enable ingress`
- 지금 필요? 브라우저 접근/도메인 테스트를 원하면 강추. 
    (간단 테스트는 `kubectl port-forward`로도 됨)
---
`deploy/k8s/hpa-api.yaml`
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
  namespace: app-dev
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```
`hpa-api.yaml` — HPA(오토스케일러)
- 무엇: API의 CPU 사용률 60% 넘으면 레플리카 자동 증가(최대 5).
- 전제: metrics-server 필요  
    `minikube addons enable metrics-server`
- 왜: “부하 ↑ → 자동 확장” 경험(면접 포인트 👍)
- 지금 필요? 실습 가치 큼.(시간 없으면 마지막 단계로 미뤄도 OK)

쿠버네티스 단계별 실습 로드맵

레벨 0 — “앱 하나 먼저 보이기”(가장 단순) 
Deployment → Pod → 컨테이너 1개 실행
- 필요: Deployment(API) 만 (혹은 Pod), `kubectl port-forward` 로 확인
- 파일: `namespace.yaml`, `deploy-api.yaml` (2개만)

(WSL 내부에서) Minikube 시작 + 컨텍스트 설정
```bash
minikube start --driver=docker
kubectl config use-context minikube
```

네임스페이스 생성(있어도 재적용 OK)
```bash
kubectl apply -f deploy/k8s/namespace.yaml
# 클러스터에 네임스페이스(app-dev)를 만든다. 
# 리소스들을 담아둘 “작업 폴더”를 만든다고 보면 돼요.

kubectl get ns app-dev
```

API Deployment 적용 + 파드 상태 확인
```bash
kubectl -n app-dev apply -f deploy/k8s/deploy-api.yaml
kubectl -n app-dev get pods
```

포트포워딩으로 접근(쿠버네티스 → 로컬 터널링)
```bash
kubectl -n app-dev port-forward deploy/api 8080:8000
```
➡️ “내 앱이 컨테이너로 떠 있다”는 것을 직접 눈으로 확인

예상결과
```bash
Forwarding from 127.0.0.1:8080 -> 8000
Forwarding from [::1]:8080 -> 8000
```
이 출력은 쿠버네티스 Deployment(api) 안의 Pod가 열어둔 8000번 포트와,  
내 로컬 8080번 포트가 터널링(연결)된 상태라는 뜻이에요.

요약: Minikube 켠다 → 리소스 적용한다 → 포트포워딩
- **Minikube 켠다** = 쿠버네티스 서버(클러스터)를 내 로컬에 띄우는 것
- **리소스 적용한다** = 그 서버에게 “앱을 배포해라”라고 선언하는 것
- **포트포워딩한다** = 클러스터 안 서버(Pod)에 내가 직접 들어갈 수 있게 연결하는 것
    
즉, 쿠버네티스 시작 = 서버를 켜는 것 이라고 정리하면 좋습니다.
다만 여기서 서버는 내 FastAPI 앱 자체가 아니라, 쿠버네티스 제어 서버 + 그 위에서 실행된 FastAPI 컨테이너라고 이해하면 더 정확합니다.

API 코드 예시 (AI 호출) 
`api/main.py`
```python
import os, httpx
from fastapi import FastAPI

app = FastAPI()
AI_URL = os.getenv("AI_URL", "http://ai:8001")

@app.get("/healthz")
def healthz():
    return {"ok": True, "ai_url": AI_URL}

@app.get("/ai/echo")
async def ai_echo():
    async with httpx.AsyncClient(timeout=3.0) as client:
        r = await client.get(f"{AI_URL}/healthz")
    return {"ai_health": r.json()}
```
포워딩으로 빠르게 확인:  
`kubectl -n app-dev port-forward svc/api 8080:80` → `http://localhost:8080/ai/echo`

레벨 3 — “브라우저 도메인 접근”(Ingress)
`deploy/k8s/ingress.yaml`

적용 + 호스트 매핑
```bash
# ingress addon은 이미 Enabled 상태
kubectl -n app-dev apply -f deploy/k8s/ingress.yaml
kubectl -n app-dev get ingress

# minikube IP 조회
MINI_IP=$(minikube ip); echo $MINI_IP

# /etc/hosts에 추가 (WSL 내부)
# (에디터로 열어 수동 추가해도 됩니다)
# 예) 192.168.49.2 demo.local
```

브라우저/CLI 테스트
```bash
curl -H "Host: demo.local" http://$MINI_IP/healthz
curl -H "Host: demo.local" http://$MINI_IP/ai/healthz
# 브라우저: http://demo.local/healthz , http://demo.local/ai/healthz
```

레벨 4 — “오토스케일 맛보기”(HPA)
`deploy/k8s/hpa-api.yaml`
중요: `deploy-api.yaml`에 resources.requests.cpu가 반드시 있어야 HPA가 정상 동작합니다.
```yaml
resources:
  requests: { cpu: "100m", memory: "128Mi" }
  limits:   { cpu: "500m", memory: "256Mi" }
```

적용 + 메트릭 확인
```bash
# metrics-server는 이미 Enabled 상태
kubectl -n app-dev apply -f deploy/k8s/hpa-api.yaml
kubectl -n app-dev get hpa
kubectl top nodes
kubectl -n app-dev top pods
```

부하 걸고 스케일 아웃 관찰
```bash
# Ingress 경로 기준 예시(healthz 엔드포인트는 부하가 작으니 부하 처리를 하는 엔드포인트로 테스트 권장)
hey -z 30s -c 50 http://demo.local/healthz

kubectl -n app-dev get hpa
kubectl -n app-dev get pods -w  # 파드가 2 → 3 → 4 증가하는지 관찰
```
