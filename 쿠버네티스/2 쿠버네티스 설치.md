```bash
# (권장) 키 파일 권한 정리
```

앱마다 필요한 파일들
각 앱(api, ai) 디렉토리 안에는 자체적으로 실행 가능한 단위가 있어야 해요:
- **코드** (`main.py`, `app/` 폴더 등)
- **Dockerfile** → 이미지를 빌드할 수 있어야 함
- **requirements.txt** → 파이썬 패키지 의존성 정의
- **.dockerignore** → 도커 이미지 빌드 시 불필요한 파일 제외
    
👉 이런 구성이 장고 프로젝트 한 덩어리처럼 독립 실행 가능한 서비스 단위가 되는 거예요.

API 앱과 AI 앱은 따로따로 만드는 게 원칙
- **API 앱**: 클라이언트 요청을 받고, 내부적으로 AI 서버에 요청을 보내는 역할
- **AI 앱**: 모델을 실행하거나 별도의 처리(추론, 분석 등)를 담당
- 👉 각각 독립된 FastAPI 앱 + 독립된 Dockerfile + 독립된 Deployment.yaml
- 이렇게 해야 서로 다른 리소스(CPU/메모리) 요구사항을 분리하고, 장애/배포를 독립적으로 관리할 수 있습니다.
    
즉, 함께 만들어도 되지만(한 앱 안에 API+AI를 합치기) → 그러면 쿠버네티스에서 독립 배포·확장이 안 됩니다.  
따라서 API 따로 / AI 독립적으로 만드는것을 권장합니다.

매니페스트(Manifest) = YAML 파일

쿠버네티스에서 `Deployment`, `Service`, `ConfigMap` 같은 리소스를 정의한 YAML 파일을 매니페스트(Manifest)라고 부릅니다.

**쿠버네티스에서 리소스(Resource)란?**
쿠버네티스가 관리하는 모든 “대상 객체”를 리소스라고 불러요.  
예를 들어:
- Namespace → 작업 공간
- Pod → 컨테이너 1개 이상 실행 단위
- Deployment → Pod를 관리하는 컨트롤러
- Service → 네트워크 접근 창구
- ConfigMap / Secret → 설정 값 저장소
- Ingress → 외부에서 들어오는 HTTP 진입점
- HPA → 자동 스케일링 규칙
    
이런 것들이 전부 쿠버네티스 “리소스”입니다.

정의한다의 의미란?
쿠버네티스는 “상태 기반” 시스템이에요.  
사용자가 “원하는 상태(desired state)”를 YAML로 정의하면,  
쿠버네티스가 그 상태를 맞춰주는 것이에요.

---
###### Docker의 관점

- Docker는 **명령 기반(imperative)** 도구에 가깝습니다.
	
- 사용자가 직접:
    `docker run -d -p 8000:8000 myapp:latest`
    → 이러면 컨테이너 1개 실행.

- 컨테이너가 죽으면? 👉 자동 복구 없음. (사용자가 다시 실행해야 함)
- 5개 띄우고 싶으면? 👉 직접 `docker run` 5번 or `docker-compose up --scale` 실행해야 함.
    
➡️ 즉, Docker는 “내가 시킨 대로 한 번 실행”이지, “원하는 상태를 유지하는 시스템”은 아님.

---
###### Kubernetes의 관점

- 쿠버네티스는 **선언적(Declarative)** 상태 기반 시스템.
    
- 사용자가 “원하는 상태(desired state)”를 정의하면:
    `kind: Deployment spec:   replicas: 3`
    → “Pod가 항상 3개 있어야 해” 라고 선언.
    
- 실제 상태가 Pod 2개뿐이면? 👉 쿠버네티스가 1개 더 띄워서 3개를 맞춤.
- Pod 하나 죽으면? 👉 자동으로 새로 생성해서 3개 유지.
    
➡️ 즉, 쿠버네티스는 원하는 상태와 실제 상태를 항상 동기화합니다.

---
디렉토리 구조로 이해하기
```
my-project/
├─ docker-compose.yml   # 로컬 개발용
├─ Dockerfile           # 이미지 빌드용
└─ k8s/                 # 쿠버네티스 운영용
   ├─ namespace.yaml
   ├─ config.yaml
   ├─ secret.yaml
   ├─ ingress.yaml
   ├─ deploy-api.yaml # 실제 컨테이너 실행과 유지 관리를 알아서 해줌
   ├─ svc-api.yaml
   ├─ deploy-ai.yaml
   ├─ svc-ai.yaml
   └─ hpa-api.yaml  # 스케일링 자동화 담당
```
`deploy-api.yaml` (Deployment)
- Pod(컨테이너) 자체를 관리하는 리소스
- 몇 개 띄울지(replica), 어떤 이미지를 쓸지, 어떤 포트를 열지, readiness/liveness probe까지 정의
- 결과: Pod는 잘 떠 있지만, Pod의 IP는 유동적이고 직접 접근하기 어렵습니다.
    
---
`svc-api.yaml` (Service)
- Pod 묶음에 고정된 엔드포인트(DNS/IP)를 붙여주는 리소스
- `selector: app=api` 같은 조건으로 Pod를 자동으로 찾아 묶습니다.
- 결과: 클러스터 안에서는 항상 `http://api:8000` 처럼 접근 가능
	
---
비유
- **Deployment** = 식당 주방에 요리사(Pod) 여러 명 고용하기 (몇 명, 어떤 요리 가능?)
- **Service** = 손님이 주문할 수 있는 “카운터” 주소 만들기 (`api`라는 간판, 내부 고정 IP)

즉, `deploy-api.yaml` → Pod를 생성/유지(앱 실행)
- `svc-api.yaml` → Pod 접근 경로 제공 (앱 접속)
- 둘이 합쳐져야 실제로 “앱이 배포되고 접근 가능한 상태”가 됩니다.
---
나머지 파일들의 역할 (보조/환경/네트워킹)
- **namespace.yaml** → 리소스들을 모아 관리할 “작업 공간”
- **config.yaml** → 환경변수(ConfigMap) (앱 설정값 전달)
- **secret.yaml** → 민감정보(비번, 토큰) 관리
- **svc-api.yaml / svc-ai.yaml** → Pod 묶음을 고정 주소로 연결 (서비스 발견/내부통신)
- **ingress.yaml** → 클러스터 외부 → 내부 서비스 라우팅 (외부 접근창구)

따라서 쿠버네티스에서는 사용자가 직접 내가 원하는 상태(desired state)를 매니페스트(YAML 파일)에 적습니다. 
그리고 `kubectl apply -f <파일명>` 을 실행하면 쿠버네티스가 클러스터 안의 실제 상태(actual state)를 내가 선언한 상태와 맞추려고 자동으로 조정합니다.

우리는 처음 쿠버네티스를 사용해보는 것이므로 가장 기초적이지만 경험을 해볼수 있는 8개의 매니페스트를 사용하여 쿠버네티스 사용의 감을 잡으며 
앱 하나 배포 → 내부통신 → 외부접속 → 자동 확장 순의 흐름으로 경험을 해보는 것이 중요합니다.

---
아래 9개 매니페스트 파일의 역할 요약
- **namespace.yaml**  리소스를 모아놓는 공간(폴더 같은 개념)
    → “내 작업 공간(폴더)” 만들기
    
- **config.yaml**  공개 환경변수 (APP_ENV 등)
    → 공개 환경변수(예: APP_ENV=dev)
    
- **secret.yaml**  
    → 비밀값(예: SECRET_KEY, DB_PASSWORD)
	
- **ingress.yaml** (라우팅규칙)
    → Ingress = 쿠버네티스 클러스터 밖에서 들어오는 HTTP/HTTPS 요청을 안쪽 서비스로 연결해 주는 관문 즉, 쉽게 말해 클러스터의 출입문이에요.
    `demo.local/` → `API` 
    - 사용자가 브라우저에서 `http://demo.local/` 접속
	- Ingress가 받아서 `svc-api` 로 전달
	- 결국 API Pod로 연결
	
    `demo.local/ai` → `AI`
    - 사용자가 브라우저에서 `http://demo.local/ai` 접속
	- Ingress가 받아서 `svc-ai` 로 전달
	- 결국 AI Pod로 연결
	
- **deploy-api.yaml** (독립된 app) 
    → API 서버 Pod를 항상 2개 이상 유지 (=컨테이너 자동 관리)
    → replicas=2 이상 설정 시, API Pod를 항상 그 개수만큼 유지 (=컨테이너 자동 관리)
    
- **svc-api.yaml**  
    → API Pod 묶음을 하나의 고정 주소(`api`)로 접근 가능
	
- **deploy-ai.yaml**  (독립된 app) 
    → AI 서버 Pod를 항상 2개 이상 유지 (=컨테이너 자동 관리)
    → replicas=2 이상 설정 시, AI Pod를 항상 그 개수만큼 유지 (=컨테이너 자동 관리)
	
- **svc-ai.yaml**  
    → AI Pod 묶음을 하나의 고정 주소(`ai`)로 접근 가능
    
- **hpa-api.yaml** (옵션) 
    → CPU 부하 따라 자동 스케일링 (2~5개)

독립된 app은 서로 다른 코드/도커 이미지/Deployment로 관리되기 때문에 각각 독립적인 서비스 단위예요.
쿠버네티스에서는 이런 독립 서비스마다 보통 Deployment + Service 한 쌍을 만들어 관리합니다.

Kubernetes 매니페스트 작성

`deploy/k8s/namespace.yaml`
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: app-dev
```
`namespace.yaml` — 네임스페이스
- 무엇: `app-dev`라는 이름의 “작업 공간”을 만들며 클러스터 안의 “폴더/공간” (이 안에 모든 리소스를 깔아놓고 정리)
- 왜: 리소스를 한 데 묶어 깔끔하게 관리(삭제/조회/권한)하려고.
- 지금 필요? ✔️ 거의 항상 추천. (없어도 되지만, 쓰는 습관이 좋아요)

`deploy/k8s/deploy-api.yaml`
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: app-dev
spec:
  replicas: 2
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
        - name: api
          image: api:dev    # minikube 내부에 빌드할 예정
          imagePullPolicy: IfNotPresent
          ports: [{ containerPort: 8000 }]
          envFrom:
            - configMapRef: { name: app-config }
            - secretRef:    { name: app-secret }
          readinessProbe:
            httpGet: { path: /healthz, port: 8000 }
            initialDelaySeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: 8000 }
            initialDelaySeconds: 15
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }
```

- 무엇: `api:dev` 이미지로 레플리카 2개를 항상 유지. 헬스 체크(프로브) 포함.
- 왜: Pod가 죽으면 자동 복구, 롤링 업데이트, 스케일 조정 등 “운영 기본기”로, Pod(컨테이너) 관리 로봇. 죽으면 다시 띄우고, 개수를 늘리고/줄임
- 지금 필요? 사실상 필수.(단순 Pod보다 Deployment가 표준)

`deploy/k8s/hpa-api.yaml`
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
  namespace: app-dev
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2  # 최소 2개
  maxReplicas: 5  # 최대 5개
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```
`hpa-api.yaml` — HPA(오토스케일러)
- 무엇: API의 CPU 사용률 60% 넘으면 레플리카 자동 증가(최대 5).
- 전제: metrics-server 필요  
    `minikube addons enable metrics-server`
- 왜: “부하 ↑ → 자동 확장” 경험(면접 포인트 👍)
- 지금 필요? 실습 가치 큼.(시간 없으면 마지막 단계로 미뤄도 OK)

- **minReplicas: 2** → 최소 Pod 수 = 2개
- **maxReplicas: 5** → 최대 Pod 수 = 5개
- **metrics.averageUtilization: 50** → CPU 평균 사용률이 50% 이상이면 스케일 아웃
    
2~5개는 Pod 개수 단위입니다.
- 아무리 CPU 부하가 없어도 Pod는 최소 2개 유지
- CPU 부하가 높아지면 최대 5개까지 늘어남
- 부하가 줄면 다시 2개까지 줄어듭니다

```yml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ai
  namespace: app-dev
spec:
  replicas: 2   # 필요하면 2 이상으로 늘리세요
  revisionHistoryLimit: 3
  selector:
    matchLabels:
      app: ai
  template:
    metadata:
      labels:
        app: ai
    spec:
      containers:
        - name: ai
          image: ai:dev # minikube가 볼 수 있는 이미지여야 함
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8001
          envFrom:
            - configMapRef:
                name: app-config # (선택) AI_URL 등 공용 설정이 있으면 활용
            - secretRef:
                name: app-secret # (선택) 비밀값 사용 시
          readinessProbe: # 서비스 트래픽 받기 전 헬스체크
            httpGet:
              path: /healthz
              port: 8001
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe: # 장애 시 자동 재시작
            httpGet:
              path: /healthz
              port: 8001
            initialDelaySeconds: 15
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          resources: # HPA가 동작하려면 requests.cpu가 반드시 필요
            requests:
              cpu: "200m"
              memory: "256Mi"
            limits:
              cpu: "1"
              memory: "512Mi"
      # (옵션) 파드가 갑자기 중지되지 않도록 종료 그레이스 기간
      terminationGracePeriodSeconds: 30
```

요약: Minikube 켠다 → 리소스 적용한다 → 포트포워딩
- **Minikube 켠다** = 쿠버네티스 서버(클러스터)를 내 로컬에 띄우는 것
- **리소스 적용한다** = 그 서버에게 “앱을 배포해라”라고 선언하는 것
- **포트포워딩한다** = 클러스터 안 서버(Pod)에 내가 직접 들어갈 수 있게 연결하는 것
    
즉, 쿠버네티스 시작 = 서버를 켜는 것 이라고 정리하면 좋습니다.
다만 여기서 서버는 내 FastAPI 앱 자체가 아니라, 쿠버네티스 제어 서버 + 그 위에서 실행된 FastAPI 컨테이너라고 이해하면 더 정확합니다.

### 레벨 1 — “쿠버네티스 방식으로 접근”(Service 붙이기)

Service(API) 매니페스트
`deploy/k8s/svc-api.yaml`

적용 + 확인
```bash
kubectl -n app-dev apply -f deploy/k8s/svc-api.yaml
kubectl -n app-dev get deploy,svc,pods -o wide
```

명령어: `kubectl -n app-dev apply -f deploy/k8s/svc-api.yaml`
결과: service/api created
해석:
`svc-api.yaml` 매니페스트를 적용해서, `api`라는 이름의 Service가 `app-dev` 네임스페이스에 새로 만들어졌다는 뜻입니다.  
이 서비스는 Pod(api)들을 하나로 묶어주는 고정 주소 역할을 합니다.

명령어: `kubectl -n app-dev get deploy,svc,pods -o wide`
(1) Deployment
```
NAME                  READY   UP-TO-DATE   AVAILABLE   AGE   CONTAINERS   IMAGES    SELECTOR deployment.apps/api   2/2     2            2           25h   api          api:dev   app=api
```
- `READY 2/2` → 파드 2개가 모두 정상 실행 중
- `UP-TO-DATE 2` → 선언된 replicas=2와 실제 상태가 일치
- `AVAILABLE 2` → 외부 요청을 받을 수 있는 상태가 2개 모두 됨
- `IMAGES api:dev` → `api:dev` 이미지를 사용
- `SELECTOR app=api` → `app=api` 라벨을 가진 Pod를 이 Deployment가 관리

결론: FastAPI 앱이 2개의 파드로 정상 실행 중이고 Deployment가 이를 관리 중

---
(2) Service
```
NAME          TYPE        CLUSTER-IP    EXTERNAL-IP   PORT(S)   AGE   SELECTOR service/api   ClusterIP   10.98.46.13   <none>        80/TCP    6s    app=api
```
- `TYPE ClusterIP` → 클러스터 내부에서만 접근 가능한 고정 IP 부여
- `CLUSTER-IP 10.98.46.13` → 서비스의 내부 IP (Pod IP와 달라요, 안정적인 고정 주소)
- `PORT(S) 80/TCP` → 이 서비스는 80번 포트로 받고, 뒷단 Pod의 8000번 포트로 전달
- `SELECTOR app=api` → 라벨이 `app=api`인 Pod들을 이 서비스가 대상으로 삼음
    
결론: API 파드 2개를 하나의 서비스(IP: 10.98.46.13:80)로 묶었음 → 내부 DNS `http://api`로도 접근 가능

---
(3) Pods
```
NAME                       READY   STATUS    RESTARTS        AGE   IP            NODE       NOMINATED NODE   READINESS GATES pod/api-56bbc8f9c4-7bnnn   1/1     Running   1 (6h36m ago)   25h   10.244.0.12   minikube   <none>           <none> pod/api-56bbc8f9c4-zwgf7   1/1     Running   1 (6h36m ago)   25h   10.244.0.10   minikube   <none>           <none>
```
- `NAME` → `api-56bbc8f9c4-xxxxx` 형식은 Deployment가 만든 Pod 이름
- `READY 1/1` → 컨테이너 1개가 정상 기동
- `STATUS Running` → 잘 실행 중
- `RESTARTS 1 (6h36m ago)` → 과거에 한 번 재시작한 기록이 있음 (예: 노드 재시작, 이미지 갱신)
- `AGE 25h` → 생성된 지 25시간 됨
- `IP 10.244.0.12`, `10.244.0.10` → Pod 내부 IP (동적으로 바뀔 수 있음)
- `NODE minikube` → 두 파드 모두 같은 노드(minikube VM)에 올라감
    
결론: Pod 2개가 정상 실행되고 있으며, 둘 다 같은 노드 위에서 동작 중

---
✅ 전체 해석 요약
- **Deployment(api)**: FastAPI 앱 컨테이너 2개를 관리 중
- **Service(api)**: 두 파드를 하나로 묶어 ClusterIP(10.98.46.13:80)로 접근 가능
- **Pods(api-… 2개)**: 실제 실행 중인 컨테이너, 모두 Running 상태
    
즉:  
👉 지금 클러스터에는 FastAPI 앱이 2개 파드(replica=2)로 실행 중이고,  
👉 `service/api`라는 서비스가 이 두 파드를 하나로 묶어서 내부 통신이 가능하게 만든 상태입니다.

내부 통신 테스트(옵션)
클러스터 내부에서 서비스 이름으로 접근이 되는지 확인합니다.
```bash
# 임시 디버그 파드 실행
kubectl -n app-dev run curlbox --image=busybox:1.36 --restart=Never --command -- sleep 3600

# 파드 안에서 curl
kubectl -n app-dev exec -it curlbox -- sh -c 'wget -qO- http://api/healthz'
# 끝나면 정리
kubectl -n app-dev delete pod curlbox
```

임시 디버그 파드 생성
명령어: `kubectl -n app-dev run curlbox --image=busybox:1.36 --restart=Never --command -- sleep 3600`
결과: `pod/curlbox created`
- `app-dev` 네임스페이스 안에 curlbox라는 이름의 Pod를 생성
- `busybox:1.36` 이미지를 사용해서, `sleep 3600` (1시간 대기) 상태로 실행
- 👉 이건 네트워크 테스트용 임시 Pod

내부에서 서비스 호출
명령어: `kubectl -n app-dev exec -it curlbox -- sh -c 'wget -qO- http://api/healthz'`
결과: `{"status":"ok"}`
- 방금 만든 `curlbox` 파드 안에 들어가서
- `wget -qO- http://api/healthz` 실행
- 결과: `{"status":"ok"}`
- 👉 Service 이름(api) 으로 접근했을 때 정상 응답이 돌아옴
- 즉, 내부 DNS 통신이 잘 된다는 걸 확인한 것

테스트 끝난 후 Pod 삭제
명령어: `kubectl -n app-dev delete pod curlbox`
결과: `pod "curlbox" deleted`
- 임시로 만든 디버그 파드를 삭제
- 👉 더 이상 필요 없으니까 깔끔하게 정리

`curlbox`라는 임시 Pod를 만들었다 → 내부 네트워크에서 `api` 서비스로 접근 테스트했다 → 응답이 잘 나왔다(`{"status":"ok"}`) → 테스트 끝났으니 파드를 삭제했다.
즉, 쿠버네티스 내부 통신이 정상적으로 연결된 것을 확인한 과정입니다.

### 레벨 3 — “브라우저 도메인 접근”(Ingress)
`deploy/k8s/ingress.yaml`

개발자가 쿠버네티스에 접근하여 테스트 할때는 직접 클러스터 안으로 터널을 뚫어서 API로 접근하여 개발 및 테스트를 합니다.

그런데 인그레스 (Ingress)란?
- 쿠버네티스 클러스터 외부(인터넷)에서 들어오는 HTTP/HTTPS 요청을 받아서,  내부의 Service로 라우팅해주는 출입문(관문)입니다.
    
즉, 외부 도메인 → 클러스터 내부 서비스로 연결해주는 게 인그레스의 역할이에요. 인그레스 야물파일을 설치하면 외부도메인을 통해 쿠버네티스 내부 서비스로 들어갈수 있습니다.

인그레스를 통해 쿠버네티스에 접근하면 쿠버네티스 클러스터 안에 있는 서비스를 직접 이용할수 있습니다. 
- **API 호출**
    - 외부 클라이언트가 `https://myapp.com/api` 로 접근 → 내부 API 서비스로 라우팅
    - Postman or Insomnia, 모바일 앱, 프론트엔드 React/Vue 앱도 이 주소를 사용
        
- **여러 서비스 연결 (경로/도메인 기반 라우팅)**
    - `/` → API 서비스
    - `/ai` → AI 서비스
    - `/admin` → Admin 서비스
    - 하나의 도메인에 여러 백엔드를 붙일 수 있음
        
- **TLS/HTTPS 보안 연결**
    - Ingress에 인증서(Let’s Encrypt, 자체 서명) 붙이면 HTTPS 자동 적용
    - 외부에서 안전하게 접속 가능
        
- **트래픽 제어**
    - 특정 경로만 허용, 리다이렉트, 부하분산 등 고급 기능 적용 가능


Ingress가 외부 도메인 요청을 쿠버네티스 내부 서비스로 잘 라우팅하는지 확인하는 과정:
적용 + 호스트 매핑
```bash
# ingress addon은 이미 Enabled 상태
kubectl -n app-dev apply -f deploy/k8s/ingress.yaml
kubectl -n app-dev get ingress

# minikube IP 조회
MINI_IP=$(minikube ip); echo $MINI_IP

# /etc/hosts에 추가 (WSL 내부)
# (에디터로 열어 수동 추가해도 됩니다)
# 예) 192.168.49.2 demo.local
```

브라우저/CLI 테스트
```bash
curl -H "Host: demo.local" http://$MINI_IP/healthz
curl -H "Host: demo.local" http://$MINI_IP/ai/healthz
# 브라우저: http://demo.local/healthz , http://demo.local/ai/healthz
```

```bash
# Ingress 경로 기준 예시(healthz 엔드포인트는 부하가 작으니 부하 처리를 하는 엔드포인트로 테스트 권장)
```

---
HPA 시나리오 사전 조건 → 부하 발생 → 관찰 → 정리

`0)` 사전 조건 체크
```bash
minikube addons enable metrics-server        # 이미 enabled 여도 OK
kubectl -n app-dev get deploy api -o yaml | grep -A3 'resources:'
kubectl -n app-dev apply -f deploy/k8s/hpa-api.yaml
kubectl -n app-dev get hpa
```
- 확인 포인트
    - `deploy-api.yaml`에 resources.requests.cpu가 있어야 함 (예: `100m`)
    - `hpa-api.yaml`의 min/max/target(예: CPU 60%) 확인

`1)` “부하용 엔드포인트” 준비 (예: /work)
API에 CPU를 쓰는 아주 단순 라우트를 **임시로** 추가하세요. (테스트 후 제거해도 됨)
```python
# api/app/main.py (예시)
from fastapi import FastAPI
import time

app = FastAPI()

@app.get("/healthz")
def healthz():
    return {"status": "ok"}

@app.get("/work")
def work(ms: int = 200):
    # ms 밀리초 동안 바쁜 연산으로 CPU 사용
    end = time.time() + (ms/1000)
    x = 0
    while time.time() < end:
        x += 1
    return {"ok": True, "ops": x, "ms": ms}
```

`2)` 부하 발생 (hey/k6로 /work 두드리기)
```bash
# Ingress로 쏘는 경우
hey -z 90s -c 40 "http://demo.local/work?ms=200"

# (Ingress 준비 전이면) 포트포워딩로도 가능
# kubectl -n app-dev port-forward deploy/api 8080:8000
# hey -z 90s -c 40 "http://localhost:8080/work?ms=200"
```

`3)` 스케일 아웃/인 관찰 (두 터미널에서 동시에)
```bash
# 터미널 A: HPA 상태 모니터
kubectl -n app-dev get hpa -w

# 터미널 B: 파드 증감 관찰
kubectl -n app-dev get pods -l app=api -w

# (선택) CPU 실시간 보기
kubectl -n app-dev top pods
```
기대 흐름
- 부하 시작 수십 초 내 TARGET > 60%로 상승 → HPA가 Desired replicas 증가(2→3→4…)
- `get pods -w`에서 새 파드가 Pending→ContainerCreating→Running으로 늘어남
- 부하 중단 후 수분 내에 점진적 스케일 인(정책/쿨다운에 따라 천천히 줄어듦)

포트폴리오 “증빙 캡처” 체크리스트
- `kubectl -n app-dev get hpa` : `TARGETS`(예: `85%/60%`)와 `DESIRED` 증가 화면
- `kubectl -n app-dev get pods -w` : 파드가 2→3→4로 늘어나는 로그 캡처
- `kubectl -n app-dev top pods` : 각 파드 CPU 사용량 상승 캡처
- `hey` 결과 요약(요청 수/에러율/p95) 캡처
- (옵션) `kubectl -n app-dev describe hpa api` : Events에 “SuccessfulRescale” 기록 캡처
